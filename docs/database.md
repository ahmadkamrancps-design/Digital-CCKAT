# Database through Milestone 7

PostgreSQL with UTF-8 encoding is the application database. SQLAlchemy 2 maps
models; Alembic controls schema changes. No table creation occurs during startup.
SQLite is used only by the quick unit-test suite, never as the application database.

Migration `0001_auth_foundation` creates:

| Table | Purpose | Constraints |
| --- | --- | --- |
| users | Preapproved identity and explicit role | Unique email and nullable unique Google sub; lowercase/trimmed email; role check |
| candidates | Approved candidate registration | Unique user mapping and roll number; nonempty roll; status check; restrictive user FK |
| auth_sessions | Revocable application session | Unique hashed token; one session per user; expiry index; cascading user FK |

IDs are application-generated UUIDs. Creation/update timestamps and session expiry
use timezone-aware PostgreSQL timestamps. Application writes update `updated_at`;
manual SQL maintenance must explicitly update it. No implicit trigger is installed.

Candidate statuses initially are APPROVED and DISABLED. A CANDIDATE user without
an approved candidate row is denied. Referential and uniqueness constraints
protect account mappings. Cross-table role/approval rules belong in the service
and will also govern future staff management APIs.

Session tokens contain 256 bits of random entropy. Only their SHA-256 hashes are
stored; session CSRF tokens are separately generated. A new login serializes on
the user row and replaces the prior session. Sessions expire after eight hours by
default. Their expiry controls login access only; future exam deadlines must be
stored separately and must never derive from session expiry.

Normal commands from `backend/`:

```bash
alembic upgrade head
alembic current
alembic check
```

Review autogenerated migrations before applying them. Downgrades can remove
candidate/session data; use them only in a disposable environment after considering
backups. Application startup must never replace this process with `create_all()`.

With `TEST_DATABASE_URL`, tests use a fresh randomly named schema per test and
actual Alembic migrations. They do not drop or modify public tables. The configured
test user must be able to create/drop schemas. Use a dedicated disposable test
database anyway. Migration tests check upgrade, downgrade, re-upgrade, and ORM
schema consistency.

## Exam domain migration

`0002_exam_domain` adds seven tables without changing existing user/candidate/session
tables. Its downgrade removes only the new domain tables. There are no seeded
subjects or questions; English, Mathematics, and Urdu remain configurable data.

| Table | Purpose | Important rules |
| --- | --- | --- |
| subjects | Configurable subject catalog | Unique uppercase code, nonempty name, active flag |
| exams | Draft/archived exam definitions | Nonempty title; optional paired schedule timestamps with positive window |
| exam_subjects | Duration and order per exam | Unique subject and sequence per exam; duration 1–1440 minutes; positive order |
| questions | MCQ/short-answer question bank | Positive decimal marks; type/grading shape; local language and direction |
| question_options | Ordered MCQ options and private keys | MCQ-only composite FK; unique order; partial unique index permits at most one correct option |
| accepted_answers | Private auto-grading values | EXACT/NUMERIC-only composite FK; nonempty/distinct raw values |
| exam_questions | Ordered paper selection | Unique question/sequence per paper; optional positive marks override; composite FKs enforce matching subjects |

Marks use `NUMERIC(8,2)` and API validation allows 0.01–10000 marks. Totals are
derived from paper selections instead of stored separately. Grading configuration
uses PostgreSQL JSONB, with JSON only for SQLite unit tests. API writes validate
the complete grading shape: MCQs have 2–8 distinct options and exactly one correct
option; automatic short answers need accepted values; MANUAL has none. Cardinality
across child rows and the JSON rules are service checks, not database triggers.
Direct database maintenance must preserve those additional invariants.

Exam subjects and paper writes serialize on the exam row. Attaching paper
questions also locks question rows, as do question edits/archival. Linked questions
cannot be edited or archived through the API. This protects paper definitions from
silent changes. Paper replacement is atomic; invalid requests preserve the previous
paper. Archived exams are read-only. Production publication and attempt snapshots
must add their own rules in later milestones.

The migration was reviewed for table order, restrictive foreign keys, nullable
grading values, unique constraint names, the correct-option index, and downgrade
order. The constraint design follows SQLAlchemy's
[composite foreign key and constraint documentation](https://docs.sqlalchemy.org/en/20/core/constraints.html).
The PostgreSQL migration test checks downgrade to the foundation preserves an
existing user, then tests complete downgrade/re-upgrade and ORM consistency.

## Attempt engine migration

`0003_attempt_engine` adds candidate exam assignments, exam attempts, subject
attempts, and answers, plus the disabled-by-default `exams.is_start_authorized`
gate. Existing exams remain unauthorized. Additional composite unique keys support
strict foreign keys from the new records; they are created before dependent tables.

| Table | Main database protections |
| --- | --- |
| candidate_exam_assignments | Unique candidate/exam mapping; restrictive candidate, exam, and actor references |
| exam_attempts | One candidate/exam and one assignment attempt; composite ownership FK; consistent status/timestamps |
| subject_attempts | Unique paper and sequence per exam attempt; composite exam/paper FKs; partial unique index allows one ACTIVE subject; state/timestamp checks; expiry index |
| answers | Unique subject attempt/paper question; composite paper/question/option FKs; MCQ/short-answer shape; nonnegative revision; 500-character short-answer limit |

Subject names, sequence, and duration are copied into subject attempts when the
exam begins. Exam configuration and relevant subject catalog records freeze while
start authorization is enabled, and remain frozen once any attempt exists. Paper
questions were already immutable while linked. No candidate prompts or keys need
to be duplicated in browser storage or leaked through public schemas.

Answer rows begin with revision 0 when a subject starts. A real answer/review change
increments the revision and records the database-clock save timestamp. Submissions
preserve raw answers. `EXPIRED` is terminal and has `submitted_at = expires_at`;
papers never started before the exam's hard cutoff have null `started_at` and the
cutoff in both expiry/submission fields. All-terminal subjects finalize the exam.

The migration downgrade drops new child tables before removing referenced keys,
restoring Milestone 2 without deleting its existing exams. Downgrading deliberately
removes attempt/answer data and belongs only in disposable verification environments
or a separately reviewed recovery process.

Grading records remain for Milestone 8. Do not
add durations or fixed subject names to foundation identity tables.

Milestone 4 adds no migration. The assigned-exam API reads existing exam-subject
rows to provide safe names, durations, and order for the CCK dashboard cards.
All existing timing, ownership, revision, and locking constraints remain in force.

Milestone 5 also adds no PostgreSQL migration. Browser recovery uses IndexedDB
database `cck-answer-recovery`, schema version 1, with `drafts` and `accounts`
stores. Draft records are keyed by verified user/attempt/subject and contain local
generation, account epoch, confirmed answers, editable drafts, and exact pending
requests. The account epoch invalidates old writers after logout. Browser records
are untrusted recovery data; PostgreSQL remains authoritative for answers, revisions,
eligibility, state, and deadlines. See [Milestone 5 handover](milestone-5.md).

## Admin portal migration

`0004_admin_portal` adds `exams.is_published`, `exams.results_released`,
`exams.result_release_at`, and `audit_events`. No identity, answer, deadline, or
attempt tables are replaced. Publication defaults true at the database/legacy
API boundary to preserve existing assignment visibility. The new portal explicitly
creates unpublished exams. Start authorization still defaults false and requires
publication plus valid papers. Result release defaults false.

`audit_events` contains UUID primary key, restrictive actor/user FK, event type,
affected record UUID, and server-generated timestamp. Services append events in
the mutation transaction; duplicate imports roll back their events as well. No
API updates/deletes events. This is an application-level append-oriented foundation,
not a tamper-proof database audit store.

Subject reordering locks the exam, checks the submitted IDs match the complete
current subject set, uses temporary unique sequence positions, then applies the
requested order in one transaction. Existing attempt/configuration locks still
apply. The migration's downgrade drops its action table and three fields while
preserving the prior exam/attempt data; it discards publication/release/action
history and is only appropriate in a reviewed recovery or disposable test context.

## Proctor monitoring migration

`0005_proctor_monitoring` adds three tables without replacing answers or deadlines:

| Table | Constraints and purpose |
| --- | --- |
| proctor_exam_assignments | Unique exam/user pair; restrictive exam/staff/actor FKs; active flag and timestamps |
| attempt_presence | One row per attempt; restrictive attempt/subject FKs; position 1–200; server-authoritative last-seen timestamp |
| session_events | Restrictive attempt/optional subject FKs; unique attempt/client nonce; indexed attempt/time; constrained source/type pairs |

Heartbeat validation enforces owning assignment, active subject, position within
its paper, five-second minimum update spacing, and at most eight events per batch.
Subject/attempt membership is checked by the service. A client cannot claim server
event types or timestamps. Event source checks also exist at the database level.
Server transition events commit with their corresponding business state; unchanged
answer/start/submit retries append no duplicate event. Existing audit events record
administrator proctor assignments/revocations.

The migration downgrade removes only these three monitoring tables. It loses their
presence/events/access configuration and preserves the existing exam/answer tables.
Upgrade/downgrade/re-upgrade and ORM comparison are verified on PostgreSQL. Neither
audit table is tamper-proof against a privileged database operator.
